# 初回の公開設定（制作担当者向け）

## 現在の前提

- GitHub：`https://github.com/worldfut/worldfut-hp`、既定ブランチ `main`
- 現在はGitHub Pagesで `worldfut.jp` を公開。リポジトリの `CNAME` も確認済み。
- Cloudflareアカウントは利用者が作成済み。接続には本人のログインが必要。
- ドメイン管理会社は未確認。WordPress.comの可能性がある。
- この作業環境のGitHub接続には、対象リポジトリへの書き込み権限がないことを確認。

## 1. リポジトリへ追加

元リポジトリのバックアップを確保し、作業ブランチを作ります。このパッケージの `src`、`public`、`content`、`scripts`、`functions`、`lib`、`tests`、`docs` と、`package.json`、`package-lock.json`、`.gitignore`、`site.config.json` をリポジトリ直下へ追加します。

既存ルートの `index.html`、`worldfut_hp.html`、`admin/`、`CNAME` はそのまま残せます。Cloudflareは `dist/` を公開するので、これらとは独立します。GitHub Pagesの元ページはDNS切替まで引き続き利用できます。

最初は作業ブランチでCloudflareのテスト公開を行います。CMSから保存するブランチも、テスト中は `site.config.json` の `branch` を作業ブランチ名に合わせてください。本番運用時に `main` に戻します。ドメインはまだ接続しません。

## 2. Cloudflare PagesにGitHubを接続

CloudflareでWorkers & PagesからPagesプロジェクトを作成し、Gitリポジトリを接続します。Cloudflare GitHub Appに許可するのは原則 `worldfut/worldfut-hp` のみです。初回のアクセス許可は利用者本人が内容を確認して承認します。

設定値：

| 項目 | 値 |
|---|---|
| フレームワーク | None |
| ルートディレクトリ | リポジトリ直下 |
| ビルドコマンド | `npm run build` |
| 出力ディレクトリ | `dist` |
| Node.js | 22以上 |
| 本番ブランチ | テスト中は作業ブランチ、切替後は `main` |

ログイン用の `functions/` はリポジトリ直下に置きます。Cloudflareのダッシュボードへの静的ファイルのドラッグ＆ドロップだけでは、このログイン処理を含めた構成は完成しません。Git連携でデプロイします。

## 3. GitHubで管理画面用OAuth Appを登録

テスト公開後に得られた実際の `https://プロジェクト名.pages.dev` を使用します。以下の `CMS_ORIGIN` はそのURLのオリジン（末尾 `/` なし）です。

GitHub → Settings → Developer settings → OAuth Apps → New OAuth App：

- Application name：WorldFut CMS
- Homepage URL：`CMS_ORIGIN`
- Authorization callback URL：`CMS_ORIGIN/api/callback`

発行されたClient IDとClient Secretを、Cloudflare Pagesの環境変数／Secretsへ本人が設定します。Secretをチャット・HTML・GitHub・スクリーンショットに貼らないでください。

| 名前 | 値 | 種別 |
|---|---|---|
| `GITHUB_REPO` | `worldfut/worldfut-hp` | 環境変数 |
| `CMS_ORIGIN` | 実際のテスト用URL、末尾 `/` なし | 環境変数 |
| `GITHUB_CLIENT_ID` | OAuth AppのClient ID | 環境変数 |
| `GITHUB_CLIENT_SECRET` | OAuth AppのClient Secret | Secret（暗号化） |
| `GITHUB_SCOPE` | 公開リポジトリは `public_repo` | 環境変数 |

`GITHUB_REPO` と `CMS_ORIGIN` はビルドとFunctions実行時の両方で参照します。設定後は再デプロイが必要です。GitHub OAuth Appに有効期限付きトークンを強制する設定は使用しないでください。この実装はトークン更新に未対応です。

OAuthの `public_repo` 権限は利用者が書き込める他の公開リポジトリにも及びます。サイト用アカウントでの利用が適しています。サイトを非公開リポジトリにする場合は `repo` 権限が必要となり、アクセス範囲が広がるため事前に構成を再検討してください。Cloudflare GitHub Appのリポジトリ限定権限と、このCMSログインのOAuth権限は別物です。

## 4. テスト用URLで確認

1. `/` が表示され、写真・スライド・活動タブが動くこと。
2. `/admin/` からGitHubでログインできること。編集者には対象リポジトリのWrite権限が必要。
3. テスト記事を作り、写真と本文を入力。「HPに掲載する」をオンにして「公開」→「公開する」。
4. Cloudflareのビルド完了後、HPと詳細ページに反映されること。
5. 「HPに掲載する」をオフにして保存後、一覧と詳細ページが公開されなくなること。
6. テスト記事と不要なテスト画像を片付けること。
7. お問い合わせフォームを利用者が実送信し、受信を確認すること。既存Web3Formsの設定を引き継いでいるが、送信・受信は別途確認が必要。

既存CAMPFIRE記事にはプレビュー用URLが含まれています。公開用のURLが別にある場合は、管理画面で差し替えてください。

## 5. worldfut.jpの切替

テストが完了し、内容を確認したら作業ブランチをmainへマージし、Cloudflareの公開ブランチと `site.config.json` の `branch` を `main` に合わせます。

ドメイン管理会社のログインとDNS設定を確認します。WordPress.comの場合、ドメイン契約とサイト契約を混同せず、ドメイン契約を維持します。

Cloudflare Pagesでカスタムドメインとして `worldfut.jp` を追加します。ルートドメイン利用には、原則としてCloudflareのDNSゾーンを設定し、管理会社でネームサーバーを変更する必要があります。**現在のDNSレコードとDNSSECの有無を先に確認し、メール用MX・TXTや既存サービスの設定を保存・引き継ぎます。** DNSSECが有効な場合はCloudflareの公式移行手順に従い、管理会社側のDSレコードも適切な順序で扱います。

公式手順：https://developers.cloudflare.com/pages/configuration/custom-domains/

管理画面を `https://worldfut.jp/admin/` にする段階で：

- `CMS_ORIGIN` を `https://worldfut.jp` に変更。
- OAuth AppのHomepage URLとcallbackを本番URLに変更。
- Cloudflareを再デプロイし、ログインと更新を再確認。

移行直後はGitHub Pagesの元ファイルを残しておきます。不具合時は以前のDNSレコード／ネームサーバーを復元できるようにします。安定運用後、GitHub Pagesの旧公開設定を整理してください。

## 6. 引き継ぎ

- GitHub・Cloudflare・ドメイン管理会社はそれぞれ管理者を複数人にする。
- 編集者には各自のGitHubアカウントを使ってもらう。パスワードを共有しない。
- 交代時は新担当者を招待して更新確認後、旧担当者の権限を外す。
- ドメイン更新日・支払担当・契約メールアドレスを団体で記録する。
- 日常更新は管理画面。ログイン設定やツールの保守は制作担当者が行う。
